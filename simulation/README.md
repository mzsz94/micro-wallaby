# microWallaby Motion Lab

하드웨어 조립 전 **5개 구동축의 움직임·주행·도킹 상태 전이**를 확인하는 로컬
시뮬레이터입니다. NU-87/Zephyr 바이너리를 실행하는 에뮬레이터가 아닙니다.
원격 API, npm 패키지, CDN, 인터넷 접속 없이 동작합니다.

## 실행

저장소 루트에서:

```sh
python3 simulation/serve.py
```

브라우저가 자동으로 열립니다. 주소는 `http://127.0.0.1:8765/`이며 종료는
터미널의 `Ctrl+C`입니다. `simulation/start.command`를 실행해도 됩니다.
사용 중인 포트라면 `python3 simulation/serve.py --port 8766`을 사용하세요.
브라우저 자동 열기를 끄려면 `--no-browser`를 추가합니다.

Python 3와 ES module·Canvas를 지원하는 최신 브라우저가 필요합니다.
`index.html` 파일을 직접 여는 `file://` 방식은 모듈 로딩 제한 때문에 지원하지 않습니다.
서버는 **127.0.0.1**에만 열리고 `simulation/`만 제공합니다. 다른 PC에서는 ZIP을
받아 해당 PC에서 실행합니다. NU-87 연결, SDK, west, Rosetta는 이 시뮬레이션에 필요하지 않습니다.

## 기존 개발 환경과의 관계

2026-10-09 확인한 기존 작업 흐름을 기준으로 합니다.

- 개발·빌드: Apple Silicon Mac mini. 이 작업 검증 시 Python 3.14.3, Node 25.8.1.
- MacBook: Mac mini에서 만든 ZIP을 받아 실행. 실기 시험 때는 별도 펌웨어 ZIP을 플래시.
- 펌웨어: `west.yml`의 고정 Zephyr revision, `nucode_nu87`, 기존 Zephyr SDK 1.0.1 경로 유지.
- 최근 얼굴 구성: NU-87, Waveshare LCD1602 I2C 23991, NU-IMU-LSM6DS3TR, USB-C 전원.
- 실제 얼굴 케이스는 128 × 162.2 × 41 mm, M3 60 × 20 mm 차체 인터페이스가 있는 설계.
  화면의 로봇은 이 구성을 참고한 개념도이며 STL·실제 치수의 강체 모델이 아닙니다.
- 실제 차체·바퀴 모터·배터리가 아직 확정되지 않았으므로 이전 v0 목표를 가상 모델로 사용합니다.
  현재 체크아웃의 I/O bring-up 코드는 모터·도킹을 구현하지 않습니다.

## 먼저 해 볼 실험

1. **기본 도킹**에서 ‘자동 도킹’을 누릅니다. 탐색 → 접근 → 최종 정렬 → 접점 →
   5초 확인 → `CHARGING`을 관찰합니다. 재생 속도 4×로 빠르게 볼 수 있습니다.
2. **옆에서 정렬**에서 같은 실험을 반복합니다. 로봇이 회전하며 접근하는 경로를 봅니다.
3. **가려진 도크**에서는 신호가 가려져 탐색 시간 초과로 실패하는지 확인합니다.
   장애물 회피·지도 탐색은 구현 범위가 아닙니다.
4. 이동 중 **E-stop**, **범퍼**, **낭떠러지**, **IMU 기울어짐 확정**을 주입합니다.
   원인을 꺼도 자동 재개하지 않습니다. ‘오류 해제’ 후 새 명령을 내립니다.
5. **충전 실패**를 켜고 도킹합니다. 한 번 재시도한 뒤 두 번째 실패에서 정지합니다.
6. **배터리 24%** 시나리오는 자동 도킹합니다. 슬라이더를 15% 미만으로 내리면
   이동을 차단합니다. 실물 USB 전원 구성에 배터리가 있다는 뜻은 아닙니다.
7. 머리·허리 슬라이더 또는 ‘환영 동작’으로 표현성을 봅니다. 도킹 중 환영은
   접점 안정 조건에서만 ±15°, 최대 3초로 제한합니다.

수동 주행은 방향 버튼을 누르는 동안 또는 W/A/S/D·방향키로 제어합니다.
입력창·버튼에 키보드 포커스가 있으면 해당 컨트롤의 기본 조작을 우선합니다.
Space로 정지합니다. 자동 도킹을 ‘정지’한 뒤 수동 입력하며, 창 포커스를 잃으면 입력을
해제합니다. 보이지 않는 탭에서는 시뮬레이션 시간도 정지합니다.
통신 단절은 수동 주행을 중단하며 로컬 센서가 정상인 자율 도킹은 계속됩니다.

‘실험 로그 저장’은 설정·시나리오·사용자 조작·최종 상태·최근 이벤트를 JSON으로
내려받습니다. 로그 가져오기/자동 재생 기능은 아직 없으며, 테스트 재현은 아래
headless API를 사용합니다. 브라우저 새로고침 시 실험 상태가 초기화됩니다.

## 구동축과 모델 파라미터

`model.mjs`의 `CONFIG`가 물리·제어 상수의 단일 정의입니다.

| 항목 | 현재 값 | 출처/성격 |
| --- | --- | --- |
| 바퀴 좌·우 | 속도 제어 2축 | 기존 v0 차동 구동안 |
| 머리 yaw/pitch, 허리 yaw | 위치 제어 3축 | 기존 v0 표현 관절안 |
| 바퀴 지름 / 윤거 | 60 / 150 mm | `docs/architecture.md` §6.1의 설계 목표 |
| 최대 선속도 / 가속도 | 0.15 m/s / 0.3 m/s² | 같은 문서 §6.1 |
| 제어 간격 | 20 ms (50 Hz) | 같은 문서 §8.1 |
| 접근 / 정렬 속도 | 0.08 / 0.03 m/s | 같은 문서 §7 |
| 최종 정렬 거리 | 표면 간격 150 mm | 같은 문서 §7 |
| 도크 감지 범위 | 2 m, 시야 내·장애물 없음 | 기존 제한 환경을 이상화 |
| 충전 확인 / 시도 상한 | 5초 / 2회 | 같은 문서 §7 |
| 저배터리 | 25% 미만 도킹 / 15% 미만 이동 금지 | 같은 문서 §12 |
| 머리 yaw | −60° ~ +60° | **임시 가정**, 실측 전 |
| 머리 pitch | −25° ~ +35° | **임시 가정**, 실측 전 |
| 허리 yaw | −30° ~ +30° | **임시 가정**, 실측 전 |
| 로봇 충돌 반경 | 100 mm | 임시 원형 footprint |
| 최대 회전 속도 | 1.5 rad/s | 시뮬레이션 가정 |
| 충전 속도 | 초당 0.25%p | 시각화용. 방전·전기 모델 없음 |

**5개 구동축이 공간에서 독립 이동하는 5자유도라는 뜻은 아닙니다.** 바퀴의
회전 2축이 전진 속도와 차체 회전 속도를 만듭니다. 차체 자세는 `(x, y, θ)`로
기록하지만 바퀴의 옆미끄럼을 금지하므로 횡방향으로 바로 움직일 수 없습니다.

좌표는 x 오른쪽, y 위쪽, θ는 +x 기준 반시계 방향 라디안입니다.
바퀴 반지름 `r`, 윤거 `b`, 바퀴 각속도 `ωL`, `ωR`에 대해:

```text
v = r (ωR + ωL) / 2
ω = r (ωR - ωL) / b
dx/dt = v cos θ, dy/dt = v sin θ, dθ/dt = ω
```

`snapshot().velocity.left/right`는 바퀴 접선 **m/s**이고 UI는 반지름으로 나눠
**rad/s**를 표시합니다. `wheelAngles`는 rad, `joints`는 degree입니다.
관절 속도 제한·질량·관성·모터 토크는 물리적으로 계산하지 않습니다.

## 검증 범위와 가정

- 도킹 제어기는 이상적인 도크 위치와 접근 지점을 사용합니다. 실제 좌우 IR 세기로
  이 위치를 추정하는 알고리즘, 가림에 강한 탐색, SLAM은 구현하지 않았습니다.
- 원·벽의 기하학적 충돌과 fault 정지를 모델링합니다. 마찰·관성·미끄러짐·충돌력·
  전복·정지거리·서보 발열의 물리 검증을 대신하지 않습니다.
- 충전 실패 후 재시도는 **가상 스프링이 접점을 1 cm 수동적으로 해제한다는 가정**을
  사용합니다. 접점이 활성화된 동안 바퀴를 구동하지 않기 위한 단순화입니다.
  실제 기구의 접점 해제·후퇴 정책을 확정해야 하며, 이 모델로 기구 타당성을 판단할 수 없습니다.
- IMU 토글은 `35° 초과가 200 ms 이상` 지속되었다는 **판정 결과**를 주입합니다.
  NU-IMU I2C 드라이버·raw 데이터·bias 보정·센서 장착축을 실행하는 기능은 아닙니다.
- E-stop은 소프트웨어상의 정지 사건입니다. 실물의 모터 전원 차단 회로나 독립
  watchdog을 검증하지 않습니다. 실제 전압·전류·온도·인증·통신 드라이버도 모델 범위 밖입니다.
- 기구 관절 숫자는 측정 후 정해야 한다는 기존 PoC 방침을 유지합니다. 2축 고정형
  PoC를 변경하지 않고, 이번 사용자가 선택한 이동·도킹 확장 실험으로 관리합니다.

## 파일 책임과 테스트

```text
simulation/
├── model.mjs         # DOM 없이 실행되는 결정론적 운동학·상태·센서 모델
├── model.test.mjs    # Node 기본 test runner로 경계·실패·회귀 검증
├── app.mjs           # 입력·Canvas 렌더링·로그 내보내기
├── index.html        # 화면 구조
├── style.css         # 반응형 스타일
├── serve.py          # 표준 라이브러리 localhost 서버
├── start.command     # macOS 실행 진입점
├── package.py        # allowlist로 전달용 ZIP 생성
└── dist/             # 생성 ZIP (Git 제외)
```

테스트에는 Node 22 이상이 필요합니다. `npm install`은 필요하지 않습니다.

```sh
node --test simulation/model.test.mjs
node --check simulation/app.mjs
python3 -m py_compile simulation/serve.py simulation/package.py
make -C firmware/nu87_io_bringup/tests/host test
```

모델 API는 화면과 독립적입니다. 파라미터·동작을 바꾸면 동일한 Node 테스트로
회귀를 확인하고 브라우저에서 표시 단위·입력·정지를 확인합니다.

```js
import { Simulator } from './model.mjs';
const robot = new Simulator('default');
robot.command('dock');
for (let i = 0; i < 3000; i++) robot.step(); // 60 simulated seconds
console.log(robot.snapshot().state);
```

기존 C host 테스트는 현재 펌웨어 소스를 검사합니다. 새 JS 테스트는 아직 실물로
구현하지 않은 동작 모델을 검사하므로 둘의 통과를 같은 검증으로 합산하지 않습니다.

## MacBook 전달과 GitHub 관리

```sh
python3 simulation/package.py
```

`simulation/dist/micro-wallaby-simulation.zip`을 MacBook에 옮겨 압축 해제하고,
해당 폴더에서 `python3 serve.py`를 실행합니다. Python 3가 MacBook에 설치되어
있는지 `python3 --version`으로 먼저 확인하세요. Node는 UI 실행에는 필요하지 않습니다.

기존 저장소 `mzsz94/micro-wallaby` 안에서 펌웨어·기구와 같은 버전으로 관리합니다.
별도 중첩 Git 저장소는 만들지 않습니다. 새 기능은 `feat/` 브랜치에서 작업하고
시뮬레이터 소스·테스트·문서를 함께 변경합니다.

`.github/workflows/simulation.yml`은 변경 시 Node 22/Python 3.12에서 검사 후
MacBook 전달용 ZIP을 Actions artifact로 생성합니다. 이 파일을 GitHub에 push한
뒤에 해당 workflow가 실행됩니다. ZIP·캐시는 `.gitignore`로 제외합니다.
현재 로컬 서버 주소는 다른 기기나 인터넷에서 접근하는 공유 링크가 아닙니다.
