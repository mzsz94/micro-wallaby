OTA CLI의 `inspect`는 구조와 SHA-256만 검증한다. 공개키 서명 확인은 별도의
`imgtool verify`와 장치의 MCUboot가 담당한다.

## NU40 실물 초기 설치와 부팅

이후 사용자가 연결한 NU40DK를 USB 식별값으로 확인했다. 당시 앱은 참고 저장소의
OLED 전용 버전과 달리 `firmware=3`, `version=0.1.4`, `transport=smp_ble`를 보고했다.
USB 부트로더로 전환해 `Board-ID: BARAM-NU40`, `SoftDevice: not found`,
부트로더 `60c185b`를 확인하고 기존 `CURRENT.UF2`와 `INFO_UF2.TXT`를 비공개로 백업했다.

기존 이미지에는 새 레이아웃의 primary trailer 페이지에 4,046바이트의 비어 있지 않은
데이터가 남아 있었다. Sparse UF2는 해당 페이지의 다른 바이트를 보존하므로, 초기 설치
생성기를 보완해 `0x1000–0xdffff` 전체를 명시적으로 기록하도록 했다. 검증된 MCUboot와
confirmed 앱 이외에는 이전 OTA 상태·secondary slot·NVS·BLE 페어링을 초기화한다.
MBR `0x0–0xfff`와 USB 복구 부트로더 `0xe0000+`는 기록 대상에서 제외한다.
이 초기화는 factory UF2에만 적용하며 이후 signed SMP OTA에는 적용하지 않는다.

- 3,568개 UF2 블록의 주소·번호·family ID·magic과 원본 HEX 일치를 독립적으로 검사했다.
  primary image_ok=1 및 MCUboot magic 보존, secondary/NVS의 erased 값도 확인했다.
- 최종 UF2 1,826,816바이트 전송을 완료하고 새 USB 제품명
  `military-wallaby NU40 voice`로 재등장한 것을 확인했다.
- 실제 부팅 로그: `role=military-wallaby firmware=2`, `oled_init=0`,
  PDM `ready=1 rate=16000 frame=176`, BTN4 `P1.05 init=0`, BLE 초기화·광고 결과 0.
- BLE 연결과 ATT MTU 247 협상도 관찰했으나, 그 연결의 중앙 장치가 NU87인지는
  이 USB 로그만으로 확인하지 않았다. 전체 플래시 readback 비교는 수행하지 않았다.

백업은 Git 제외 경로 `build/nu40-backups/`, 새 부팅 로그는
`build/nu40-device-validation/boot.log`에 저장했다. 실제 음질·스피커 가청 출력 및
NU87 경유 OTA 업로드·시험 부팅·확정·롤백은 아직 검증하지 않았다.

## BTN2/BTN3 후속 변경 (NU40 전용)

물리 버튼 기능은 NU40 앱에만 추가했다. NU87 펌웨어, BLE 오디오 프레임 형식 및
HostPC 실행 코드는 변경하지 않았다. 제조사 예제에서 BTN2=P1.07, BTN3=P1.06을
확인했다. 웹 마이크 시작은 수신 세션 준비이며, BTN2가 실제 PDM 녹음을 시작하고
BTN3가 녹음 종료와 전송을 요청한다. 최대 10초/500프레임/88KB를 RAM에 보관한다.
한도 도달만으로는 전송하지 않는다. 녹음 전송 전의 1초 간격 패킷은 순수 무음이다.

- NU40 테스트 5개와 공통 오디오·버튼 테스트 1개가 통과했다. 새 C 검사는 ASan/UBSan을
  사용하며 500프레임 한도, BTN3 전 출력 금지, 버퍼 삭제와 세션 예산을 확인한다.
  실제 `voice.c` 콜백·전송 작업을 포함한 검사에서 STOP/새 세션 뒤 대기 패킷 차단,
  알림·큐·작업 제출 실패와 경고·OTA·구독·연결 해제 처리를 확인했다.
- 기존 NU87 수신 콜백을 사용하는 ASan/UBSan 호환 검사에서 80초의 무음 연결 유지와
  500개 녹음 프레임, 40개 종료 무음 프레임을 수신했다. 총 620개, 누락 0개였다.
  64프레임 버퍼 초과와 STOP 뒤 추가 패킷 차단도 확인했다. 실물 무선 시험은 아니다.
- 실제 C ADPCM 인코더 출력 104프레임을 기존 Python 디코더·VAD로 처리했다.
  초기 무음 5프레임에서 발화가 생성되지 않았고, 녹음 전송 뒤 한 발화가 생성됐다.
- 이 ADPCM 경로의 합성 명령을 로컬 Whisper에 넣자 `왈랍이 앞으로 가`로 전사돼
  정확 문구 기반 이동 명령은 선택되지 않았다. 패킷 호환 확인을 실제 PDM 음질이나
  명령 인식 성공으로 해석하지 않는다. 실물 마이크 입력으로 인식률을 확인해야 한다.
- 기존 Host VAD는 녹음 내부에 700ms 침묵이 있으면 첫 구간을 처리하고 STOP을 보낸다.
  500프레임 시험에서는 135번째에 발화가 확정됐다. 따라서 이번 호환 모드는 짧은
  명령 한 문장용이며, 긴 녹음 전체의 일괄 처리를 보장하지 않는다.
- 연결·구독 상실, 경고, OTA, STOP 또는 새 세션은 보관 녹음을 폐기한다.
  Host 수신 화면의 5초 lease가 유지돼야 하며, 음성 응답이 끝난 뒤 다음 녹음을 시작한다.

NU40 `0.1.1+0` 앱과 MCUboot를 실제 sysbuild로 다시 빌드했으며 컴파일 경고 없이
서명 공개키 검증을 통과했다. 앱 FLASH 235,364 B, RAM 168,336 B, 서명 업데이트
파일 235,516 B다. OTA CLI도 이미지 구조와 해시를 별도로 확인했다.

- 업데이트 파일 SHA-256:
  `9ac1769d80d99de0d173f68daee76ebd4a99661c7f1b43df377f933a2e285c17`
- MCUboot 이미지 해시:
  `467a9f2ffa246d5eb6a3378932c89bcf53c8436beaf18572cced31b41cff4426`

앞선 NU40 초기 설치 결과는 이전 `0.1.0`에 해당한다. 이전 서명 이미지와 초기 설치
파일은 Git 제외 경로 `build/nu40-voice-0.1.0/`에 보관했다.

### 0.1.1 USB 설치 (2026-10-11 KST)

사용자가 NU40 직접 연결 후 설치를 요청했다. 동일 USB serial의 BARAM-NU40를 확인하고
1200 baud로 UF2 부트로더에 진입했다. 기존 `CURRENT.UF2`와 `INFO_UF2.TXT`를
`build/nu40-backups/20261011-013205-btn23/`에 백업했다. 실제 `0x1000–0x75fff`는
보관된 0.1.0 factory UF2의 MCUboot와 confirmed 앱 바이트에 완전히 일치했다.
Confirmed HEX와 별도로 서명한 OTA BIN의 ECDSA TLV 바이트는 서로 다를 수 있으므로
설치 상태 비교에는 당시 사용한 factory UF2를 기준으로 삼았다.

- 0.1.1 confirmed HEX의 공개키 서명 검증과 이미지 해시 확인을 다시 통과했다.
- 설정 보존용 UF2는 정확히 `0x10000–0xdbfff`만 기록한다. 새 confirmed 앱 이외의
  primary 영역과 secondary 영역은 FF로 채워 이전 swap 상태를 제거했다.
  MBR·MCUboot·NVS/BLE 페어링·USB 부트로더는 기록 범위에서 제외했다.
- 3,264개 UF2 블록, 1,671,168바이트의 주소·family·번호·데이터·confirmed footer를
  독립 검증한 뒤 USB 전송과 fsync를 완료했다. 파일 SHA-256:
  `fb201cff30a4ba1739141634b40b98ef045c4ff480c92ae1268a4d5606c3d104`.
- 같은 USB serial과 `military-wallaby NU40 voice` 제품명으로 재등장했다.
  실제 로그에서 `oled_init=0`, `VOICE|BOOT ready=1 ... buttons=2,3`,
  `VOICE|BTN2=P1.07 BTN3=P1.06 init=0`, `ALARM|BTN4=P1.05 init=0`을 확인했다.
- BLE 초기화·광고는 성공했으나 연결 후 MTU 협상 `error=14`, 해제 `reason=19`가
  반복됐다. 중앙 장치의 정체는 확인하지 않았으며 NU87 음성 전달 성공으로 기록하지 않는다.

설치 파일과 주소 범위를 검증하고 재부팅·초기화를 확인했으며, 설치 후 전체 flash
readback 비교나 물리 버튼을 누른 실제 음성 입력 시험은 수행하지 않았다.
설치 메타데이터와 로그는 `build/nu40-buttons-validation/usb-update.json`, `usb-boot.log`에
비공개로 보관했다. NU87 펌웨어와 HostPC 실행 코드는 변경하지 않았다.

- `왈라비 폭발물 탐지해`를 기존 훈련 탐색 명령으로 연결했다. 질문·부정·인용·보고와

1.4초에서 이 지연을 재현했다. 실물 손실률은 측정하지 않았고 누락 감지 시 발화 폐기는
기존대로 유지한다.

## Windows/WSL 후속 통합과 재연결 수정 0.2.2

`test/military-wallaby`의 `bbe6904`, `e7944d1`, `f114e33`과 후속 그래픽·음성 통합
`cd1be65`, `4403ba9`를 `feat/military-wallaby-oled-graphics`에 통합했다. NU40 소스와
검사는 소유 저장소의 `feat/military-oled-graphics`에도 반영했다.

실물 `0.2.1`을 NU87의 인증된 BLE SMP로 업로드하고 정확한 이미지 해시를 확인해
시험 부팅했다. OLED 드라이버 ACK는 받았지만 마이크 START는 HTTP 422/장치 오류
`-5`, 경보 해제는 ACK를 받지 못했다. 해당 이미지를 확정하지 않고 소프트웨어
리셋했으며, 기존 `0.2.0`이 활성·확정 상태로 복구된 것을 SMP 이미지 목록으로 확인했다.

앱의 연결 콜백이 마이크·경보의 구독 상태를 무조건 false로 설정하고 있었다.
Zephyr는 저장된 CCC를 앱 연결 콜백보다 먼저 복원할 수 있으며, 같은 CCC 값의 쓰기는
변경 콜백을 다시 부르지 않는다. 따라서 복원된 구독을 지울 수 있다. `0.2.2`는
`bt_gatt_is_subscribed`로 실제 상태를 읽고, 마이크는 명시적 START 전까지 비활성으로
유지하며, 기존 경보 래치가 있으면 ACK를 다시 보낼 수 있도록 한다.

실제 `voice.c`와 `alarm.c`를 사용하는 네이티브 회귀 검사는 CCC 조기 복원, 변경 콜백
없는 반복 연결, 새 미구독 연결을 검사한다. 수정 전 콜백에서는 구독 복원 assertion이
실패했고 수정 후에는 통과했다. 두 저장소에서 NU40 검사 10개가 통과했으며 C 검사는
ASan/UBSan을 사용했다.

`0.2.2+0`은 Zephyr `e70694102ad6`, SDK 1.0.1에서 sysbuild와 증분 빌드를 수행하고
P256 공개키 서명 검증을 통과했다. 앱 FLASH 238,932 B, RAM 168,464 B다.

- MCUboot 이미지 해시:
  `9f46926b733401b928594d3b41eec0938f35078378cf80af77864a73e1024568`.
- 전송 파일 SHA-256:
  `092d891b7b40ab6ee002483e4740263c74c60300095bf3afef26c59941be9e79`.

## 절전 및 핫스팟 재시작 처리

Windows 전원 이벤트에서 2026-10-11 13:52:40~15:02:11 KST에 덮개 닫힘으로 Modern
Standby에 들어간 것을 확인했다. 이때 WSL의 monotonic 시간 진행도 멈춰, 약 70분의
실제 중단을 4분 연속 검사로 해석할 수 없었다. 해당 측정은 연속 안정성 증거에서 제외한다.

HostPC의 센서 신선도는 monotonic 경과와 wall-clock 변화 중 더 큰 값으로 판정한다.
절전 뒤 같은 센서 순번은 만료 상태를 유지한다. 새 순번이 와도 중단 전의 기준 자세
측정·기울기 지속 시간·가상 탐색 요청은 이어 붙이지 않는다. 이미 확정한 기준 자세는
보존한다. 시계 역방향 보정과 VM 시간 정지를 포함한 Host Python 146개가 통과했다.

핫스팟 재시작 후 실제 채널이 1에서 6으로 바뀌었고, 이전 NU87 이미지에서 AP 검색
실패 `-4108`이 반복됐다. 설정 채널은 부팅 후 첫 접속의 힌트로만 사용하고, 이후 시도는
2.4GHz 전체 채널을 검색하도록 변경했다. 실제 `wifi.c` 함수의 힌트·재시도·DHCP·취소
결정을 ASan/UBSan으로 검사했으며, NU87 Python 검사 78개가 통과했다. 소스를 먼저
`c3ccab9`로 푸시한 뒤 실제 NU87에 자동 ROM 진입으로 기록했다. Zephyr 빌드 결과는
FLASH 622,000 B, RAM 210,774 B였다. 실제 부팅에서 채널 1의 첫 시도가 실패한 뒤
채널 255(전체 검색)의 두 번째 시도가 성공했고, 부팅 약 38.3초에 DHCP 주소를 받았다.
알고 있는 NU40을 다시 선택해 실제 IMU 입력·센서 오류 0과 OLED ACK를 확인했다.

이후 121.49초(실제 시간과 monotonic 최대 차이 약 9ms) 검사에서 새 IMU 423회,
만료 관측 0/600, 최대 수신 공백 1.44초와 센서 오류 0을 확인했다. OLED ACK는
94회, 최대 공백 4.20초였고 BLE 이유 `0x08` 종료 1회 뒤 같은 장치로 자동 복구했다.
이 구간에 NU87 가동 시간 역행은 없었다. 입력 수신은 복구됐지만 BLE 연속 안정성은
남아 있으며, 근거 없는 RF 설정이나 만료 기준 변경으로 가리지 않았다.

## 0.2.2 OTA 및 확정 후 재연결 실물 확인

서명 이미지 239,083 B를 NU87 Wi-Fi → 인증 BLE SMP → NU40으로 전송했다. 첫 시도 실패와
후속 BLE 시간 초과가 있었으며, 재연결 뒤 같은 이미지의 전송을 재개해 완료했다. 정확한
이미지 해시를 조회하고 시험 부팅했다. OLED ACK·경보 해제 ACK와 마이크 START/STOP을
확인한 뒤에만 그 해시를 명시적으로 확정했다. 다시 소프트웨어 리셋한 후에도 활성·확정
`0.2.2`와 같은 해시가 유지되고 위 세 경로가 정상 동작했다.

각 부팅의 오디오 검사에서는 준비 무음 프레임 순번 0, 1, 2를 디코딩했고 누락 0,
최대 PCM 절댓값 0이었다. BTN2/BTN3를 누르지 않았으므로 음향 녹음 검증은 아니다.
수정 전 `0.2.1`에서 실패하던 준비·ACK가 저장된 BLE 구독의 반복 연결에서 복구된
것을 확인했다. 경보 해제 ACK는 BTN4의 가청 출력 시험을 대신하지 않는다.

확정 후 실제 서버에서 얼굴·수평계·텍스트, 가상 탐색, W 키 주행, Space 정지의 브라우저
검사 5개 지점이 통과했고 JavaScript 오류 0이었다. 실제 센서는 책상에 내려놓았으며
새로운 값이나 시계를 주입하지 않았다. 24.92초 GIF/MP4와 확인 범위는
[`docs/demo/OLED-GRAPHICS.md`](../docs/demo/OLED-GRAPHICS.md)에 있다.

## 남은 실물 시험

### 연결 매개변수 조정

고정된 Zephyr의 `Kconfig.gatt`에서 NU40 기본 선호 감시 시간 `42`의 단위가 10ms임을
확인했다. NU87 초기 연결 기본값은 4초다. 선택한 NU40의 더 짧은 요청만 4초로 조정하고,
완료 콜백에서 실제 적용값을 별도로 기록하도록 했다. 실제 BLE 어댑터를 포함하는
ASan/UBSan 검사에서 짧은 요청 조정, 긴 요청 보존, 다른 연결 무변경, 완료 기록과 종료
후 무효화를 검사했다. NU87 Python 78개와 네이티브 KIT·오디오·SMP·경보 검사가 통과했다.
이 변경은 물리 BLE 시간 초과 원인의 확정이 아니며, 적용 결과와 지속 시간은 별도 기록한다.

NU87 다운로드·Wi-Fi 부팅과 NU40 초기 설치·주변장치 초기화는 위와 같이 확인했다.
다음은 벤치 검증이 필요하다.

1. 인증 HTTP·BLE 연결 이후 장시간 Wi-Fi·BLE 연속성, 핫스팟 재시작 후 재접속.
2. 키트 배선, PDM 음질·잡음, BLE 오디오 처리량과 프레임 손실.
3. BTN4를 눌렀을 때 실제 스피커 경고음, NU87 경고 상태와 화면의 정지·해제.
4. OTA 전송 중 전원 차단 복구. 업로드·시험 부팅·명시적 확정은 위에서 확인했다.
5. 더 많은 무선 단절·전원 차단 조건의 복구. 미확정 리셋 롤백은 0.2.1 → 0.2.0에서 확인했다.

드라이버 ACK는 가청 출력 측정이 아니다. NU87의 기존 테스트 난수 생성기 등 개발 포트의
제한도 유지된다. 이 기록은 실물 음질·무선 안정성·제품 수준 보안을 검증했다고 뜻하지 않는다.
